# Backend security and booking reliability: first implementation

This branch is intended for coordinated review with the frontend booking-receipt change. It has not been deployed to production.

## Changes

- Customer single-booking reads include the authenticated owner's email in the database query. Flight ticket/provider details require either a verified owner session or a signed, booking-specific receipt token. Public Firm/API-key headers do not grant ticket access.
- New guest and third-party flight reservations return `booking_access_token`, signed for audience `borderless-booking-receipt` and valid for one day, bound to both firm and booking reference. The companion frontend stores it in session storage and attaches it as an Authorization bearer token on ticket-detail requests. It is not placed in URLs. Storage-disabled guests must sign in as the booking owner to retrieve details. Receipts without a firm claim fail closed.
- Browser payment amount/time are not financial authority. Paystack verification must confirm success, exact reference, stored amount (minor units), currency, booking-reference metadata and customer email before local recording. Existing bookings without currency use NGN, matching the current frontend checkout. Other currencies require explicit stored currency and matching checkout configuration.
- Receipt claims use MongoDB's unique `_id` index. Payment, booking, sale, host earning and host balance changes use a single transaction. Repeating the same successful payment is idempotent; a reference cannot pay a different booking. Legacy partial financial records are rejected for reconciliation rather than silently repaired.
- `POST /api/v1/website/paystack-webhook` verifies raw-body signatures and uses the same verified recording service. It can record a successful charge when the browser callback is lost. Configure this URL in the existing Paystack account only after validation. Unknown unrelated charge events are acknowledged without changing records. Email delivery from webhook-only completion is not implemented; a transactional notification outbox remains follow-up work.
- Dedicated Paystack signing secrets use `PAYSTACK_WEBHOOK_SECRET` (and optional `PAYSTACK_WEBHOOK_PREVIOUS_SECRET` for rotation), the `Paystack-Signature` header, HMAC-SHA512 and a five-minute timestamp window. When no dedicated secret is configured, existing accounts use `PAYSTACK_SECRET` and legacy `x-paystack-signature`. Once a dedicated signing secret is configured, legacy signatures cannot downgrade verification.
- Tiqwa callbacks are treated as untrusted hints. Status is fetched server-side from Tiqwa and its booking reference is matched before applying an allowed update. Late notifications cannot downgrade issued/cancelled tickets. This verifies the authoritative data; it does not claim cryptographic authentication of the incoming callback. Obtain Tiqwa's supported signing/shared-secret contract before adding incoming authentication or IP restrictions.
- Website flight creation persists a deterministic attempt before the provider POST. Uncertain attempts are not automatically retried. A confirmed provider reference/result is saved before local booking/sale writes; those local records and attempt completion commit atomically. A local write failure can resume without creating another provider reservation. Airport-catalogue retrieval is no longer required to save a provider booking; city labels initially use airport codes.
- Third-party booking now uses that same recovery flow. It preserves the provider response under `data` and adds the receipt at top level. The provider response is stored in the private attempt record so retries can return the same result without a second reservation. These records may contain passenger details and must be treated as private booking data, excluded from application logs and public APIs. Identical firm/offer/body retries are protected; changing an offer or request body is a different attempt. This is not provider-level deduplication across different offers.
- The client-controlled `admin` query parameter cannot mark a reservation paid.
- Public customer/host/waitlist directory routes require admin authentication. Profile updates allow only contact fields; notification preferences cannot overwrite account security fields; review updates require ownership. Authentication logs no longer print tokens/session records/OTPs in the changed paths. API responses default to private, no-store. Async Express 4 handler errors reach the global error middleware, and session issuance fails when persistence fails.
- Host profile updates allow only name, phone and gender, cannot overwrite password, email, approval/verification or account counters, and exclude the password from responses. Host notification reads and updates are scoped to their owner.
- Host withdrawal requests reject zero/negative/non-numeric amounts and sub-kobo precision. Bank details must match a saved account owned by the host and are copied from storage. A conditional balance debit and pending withdrawal record share one transaction, preventing concurrent overspending and partial debits. This only creates a withdrawal request; it does not initiate a bank transfer. Existing floating-point balance storage is retained: a minor-unit ledger migration and request idempotency still need separate work.
- Host listing availability, single-listing and single-booking routes require host authentication and ownership. Listing writes allow only explicit property-description/amenity/price fields, not owner, status, Mongo operators or administrative timestamps. Bookings returned to hosts omit partner keys. Host confirmation/decline applies only to pending, unpaid bookings and commits the decision and notification in one transaction; competing decisions cannot both succeed. Existing confirmation-email delivery remains outside that transaction.
- Both shortlet booking paths validate calendar dates and property availability and calculate totals from saved room rates. The current frontend's nightly-price field is accepted only when it matches an available saved rate; a new optional `room_type` selects the saved rate explicitly. Arbitrary client prices are rejected. This does not provide inventory allocation or date-overlap protection.
- Withdrawal rejection is pending-only and returns reserved funds once, atomically with the request and notification. Completed or processing transfers cannot be rejected. Approval persists a deterministic transfer reference and processing state before calling Paystack, converts NGN to kobo, and completes only after server-side verification of reference, amount, currency, recipient and successful transfer status. Client `transaction_id` is ignored. Subsequent approvals verify the same transfer; they never repeat recipient/transfer creation. Pending/OTP responses remain processing. Timeout, failure, reversal or incomplete intent requires reconciliation before funds can be released. No OTP or provider approval protection is disabled.
- Admin sessions must refer to a current administrator and match the signed subject. Changed admin/user/host directory and profile responses exclude password hashes. Newly created administrators receive an unshared random initial password instead of the old predictable name-based password; after email verification they use the existing forgot/reset-password flow. Existing accounts are not reset by this branch. This does not establish fine-grained role permissions: current administrator routes still use the existing all-admin authorization model.
- Authentication attempts use atomic MongoDB counters shared across instances. Known-account logins allow 10 attempts per 15-minute fixed window; OTP sends allow 5 per 15 minutes; admin OTP/email verification allows 5 per 15 minutes; user/host email verification and password-reset verification allow 10 per 15 minutes; reset emails allow 5 per hour. Successful attempts count too. A limit returns HTTP 429 and `Retry-After`; database failures fail closed with 503. Counter IDs hash scope/account/window; counters expire via TTL, while the actual limit window is enforced independently of TTL cleanup. These account limits do not claim IP-based abuse, signup or DDoS protection. Admin login OTP consumption is atomic and its existing one-hour expiry is enforced even before TTL deletion.

## Deployment prerequisites

1. MongoDB must support transactions (replica set or supported sharded deployment). Standalone MongoDB is unsupported; financial writes fail closed. Confirm the production topology and database permissions before rollout.
2. Use the existing `PAYSTACK_SECRET`, `JWT_USER_SECRET_KEY`, `TIQWA_FLIGHT_API`, and `TIQWA_BEARER_TOKEN` from the production secret store. No bulk secret download is required. Never embed these in the browser.
3. Install the frontend receipt compatibility change first. The old backend simply omits the receipt field; the new backend denies reference-only ticket access. Guest confirmation tabs created before rollout may need owner login. Do not deploy the backend change alone.
   The `/flight/flight-ticket-details/:booking_reference` alias is explicitly labelled Manilla in the production router. New third-party bookings include a signed receipt; Manilla must retain it and send `Authorization: Bearer <booking_access_token>` alongside its firm/API-key headers for ticket reads. Keep this branch out of production until that integration has been verified. Historical partner bookings without a receipt need a separately reviewed scoped service credential or owner authentication. The current public Firm/API-key contract is insufficient for passenger/ticket access; do not solve compatibility by making customer details public again.
4. Test in provider sandbox/staging: guest reservation/confirmation, signed-in owner retrieval, payment success/failure/retry, webhook delivery, and browser interruption. Production providers were mocked in local tests; these are not live payment or ticketing validations.
5. Monitor 4xx/5xx payment responses and `BookingAttempt` records with state `provider_pending` or `provider_confirmed`. A pending/uncertain attempt needs support-led provider reconciliation; never delete it merely to retry the POST. An operator recovery tool and scheduled reconciliation remain to be built.
6. Existing legacy payment/booking inconsistencies and duplicate provider references need a separately reviewed read-only audit/migration. This branch does not modify historical production data or build a unique index over it.
7. Newly created withdrawal requests include `funds_reserved: true` in the same debit transaction. Historical requests without that marker cannot be approved/rejected automatically: their actual balance debit and provider history must be reconciled first. Never add that marker in bulk based only on a pending status.
8. Verify Paystack transfer access and OTP/pending behavior in the provider test environment. `processing` is not a completed payout; the admin frontend must show that distinction. Retrying approval performs read-only verification of the existing reference. An intent stuck before recipient/transfer creation is deliberately held for manual recovery. Scheduled transfer reconciliation, reversal handling and a privileged recovery interface remain outstanding.
9. Review existing administrators for predictable starter-password exposure and plan credential/session rotation separately. New admin onboarding uses verified-email password reset. Fine-grained admin role permissions and MFA policy still need an agreed access matrix and follow-up implementation.
10. The application database must allow creation/writes for the new `AuthRateBucket` collection and its TTL index. Review the fixed-window account limits against normal login and support usage before rollout. Limiting by account can temporarily throttle a victim account during an attack; it does not replace upstream abuse controls or require trusting spoofable forwarding headers.

## Validation

`npm test` runs security regressions with controlled dependencies. `npm run test:integration` starts an isolated loopback MongoDB replica set, verifies real transaction rollback/concurrency/recovery, and exercises authenticated HTTP ownership/profile restrictions. It never uses production `DB_URI` and providers are mocked. The first run downloads an official MongoDB binary. `npm run build` checks the Next.js production build.

The 8 November local continuation adds partner booking recovery/HTTP receipt tests, cross-firm receipt rejection, host profile/notification ownership tests, and real transaction tests for withdrawal validation, bank ownership, concurrent balance reservation and rollback. No live provider reservations, withdrawals, payments or production data changes are used for these checks.

Initial local continuation: 32 security tests and 13 replica-set/HTTP integration tests passed, alongside the Next.js production build. The next local continuation extends coverage to 38 security tests and 28 replica-set/HTTP tests, all passed. Added cases cover gateway request boundaries, predictable admin passwords, shortlet quoting, host booking decision races, cross-host listing/booking access, password hash exclusion, payout settlement mismatch, unknown transfer outcomes, rejection rollback and completion recovery, concurrent distributed authentication limits, rate-limit failure behavior and one-time admin OTP use. Provider transfer operations are stubbed; no actual payout or provider sandbox proof is implied. The build warns that the parent checkout's lockfile is used for workspace-root inference. No continuation changes have been pushed, merged or deployed.

Final local verification on 9 November: all 66 tests passed and the Next.js production build passed against the final code.

## Remaining scope

This is a first security tranche, not a platform-wide security certification. Follow-up includes fine-grained admin permissions and the rest of the admin/auth endpoint audit (including MFA challenge binding and resend/recovery flows), broader abuse protection beyond account authentication limits, payment initiation and reconciliation tooling, cancellation/refund and transfer reversal handling, withdrawal request idempotency, exact minor-unit balance storage, session/credential rotation, shortlet inventory consistency, and a durable notification outbox. Do not auto-retry provider booking or transfer POSTs. Historical balances and real provider payout configuration have not been certified by these tests.

Provider references: https://paystack.com/docs/api/transaction/ and https://paystack.com/docs/payments/webhooks/.

Transfer reference and amount contract: https://paystack.com/docs/api/transfer/ and https://paystack.com/docs/transfers/single-transfers/.
